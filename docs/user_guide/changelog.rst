Changelog
+++++++++

**1.6.4 (09/2026)**

- **Bug fix: a forced-landing integration that ran out of iterations between two requested times was only detected when it happened on the *last* one, so a time array straddling the state epoch could return its earliest positions silently wrong by tenths of an AU.** `Particle.integrate` and `Particle.ephemeris(interpolate=False)` clamp the step size to land exactly on each requested time in turn, and the backend gives up after `IAS15_MAX_FORCED_LANDING_ITERS` (10000) iterations on any single interval. For a time-ordered array that begins before the state epoch, the first interval is not an ordinary observation-to-observation gap: it is the entire pre-epoch arc, marched backwards from the epoch to the earliest requested time in one go, and it is the interval that overruns the cap. `budgeted_forced_landing` exists to catch exactly that and re-run with extra "dummy" landing times inserted so no interval exceeds the cap, but it decided whether to do so by asking only whether the *last* requested time had been reached. A truncated interval stops at a state that is perfectly correct for the time it stopped at, so every later interval starts on the true trajectory and lands normally, and the last requested time is reached regardless -- the check passed and the recovery never ran. A downstream user measured 14 of 444 observations wrong across six objects, 11 of them at pre-epoch times, by up to 21 degrees on the sky; reproduced here on an eccentric sub-AU orbit, the earliest landing came back 0.32 AU from the truth while every other landing was correct to ~1e-11 AU. **The same time requested on its own was always correct**, which is how the discrepancy was noticed at all: with a single requested time the last-time check *is* the whole check, so it fires and the recovery runs. Truncation is now tested per landing, against the reached times the backend reports, so a truncated interval anywhere in the array triggers the same subdivision that a truncated final interval always did. **If you passed `Particle.integrate` or `Particle.ephemeris(interpolate=False)` an array of times spanning your state epoch, and the arc back to your earliest time is a long one, the earliest positions may have been wrong.**
- **Who was exposed:** the cap is on iterations, not days, so it depends entirely on how hard the orbit is to integrate. Under the default "global" controller an eccentric near-Earth orbit (a = 0.55 AU, e = 0.80) costs about 1.26 iterations per day, so any single leg longer than roughly 7900 days -- about 22 years, an ordinary arc length for an orbit fit -- overran the cap. A main-belt object at a = 2.77 AU costs about 0.06 iterations per day and would need something like 160 years, which is why this only ever bit fast, eccentric objects. Nothing on the interpolation path (`interpolate=True`, the default) was affected: its truncation handling is per-chunk stitching, which has no equivalent blind spot. The forced-landing path is, however, the independent reference the dense path is validated against, so the defect also undermined that check.
- Internal API: the forced-landing backend now reports the time each landing actually reached. `ias15_evolve_forced_landing` keeps its five-value signature -- it is passed as a generic integrator alongside the leapfrog and dense-output backends, which share that contract -- and is now a thin wrapper over `_forced_landing_with_times`, which returns the reached times as well. The per-interval iteration cap, previously a literal in the loop condition, is the module constant `IAS15_MAX_FORCED_LANDING_ITERS`, and `FORCED_LANDING_STEP_BUDGET` derives from it rather than restating it. No change to any step sequence or to the results of an integration that was not truncating.

**1.6.3 (09/2026)**

- **Bug fix: the dense-output light-travel-time correction extrapolated the wrong IAS15 step, silently corrupting a handful of observations per arc by up to tens of arcseconds.** `Particle.ephemeris(interpolate=True)` -- the default -- and every other dense path corrected for light travel time by evaluating the polynomial of the step *containing the observation* at the retarded time `t_obs - LTT`. Whenever the light travel time exceeded that step's length, the 7th-order polynomial was used outside its own `[0, 1]` interval, where the `h**7` term amplifies converged-tolerance noise in the high-order b coefficients: an excursion of twenty step lengths reaches ~1e-3 AU. The adaptive controller shortens steps to ~1e-3 days near perihelion and through close encounters, so excursions of 5-20 step lengths are routine for an object observed from 1 AU. A downstream user measured a median error of 0.13 arcsec and a maximum of 27.5 arcsec across 98 affected archive rows, with typically only 3-4 observations per row wrong and the rest correct to a few microarcsec -- a scatter of outliers that dominates chi-square in a fit rather than a uniform small bias. **If you generated astrometry or fit orbits with `interpolate=True` across a perihelion passage or a close encounter, a small fraction of those positions were wrong.** The correct value was already in memory: the retarded time lies in an *earlier* step, whose own converged polynomial covers it at `h` in `[0, 1]`. The propagator now looks that step up and interpolates it, so accuracy no longer depends on the light-travel-time-to-step-length ratio at all. Results are unchanged (to ~1e-7 mas, float64 round-off at step boundaries) wherever no extrapolation was happening.
- **The dense-output buffers are now extended backwards past the earliest requested time**, by twice the largest topocentric light travel time. This is what makes the fix above unconditional: the retarded time of an observation at -- or within a light time of -- the state epoch precedes the whole integration, so there would otherwise be no step to look up, which is exactly the regime of the 1.5.0 distant-short-arc fix. Both directional passes are now always integrated, so an arc that only runs one way pays one extra short kernel call: measured at ~13% on the `System(observations=...)` `loglike` hot loop for a 300-day, entirely post-epoch arc (21.8 -> 24.8 ms per call at 32 walkers x 24 observations), which is the worst case for this change since the extra pass is pure overhead there. The `ltt_seed_floor` first-step seeding from 1.5.0 is retained: it is redundant for the dense paths now, but removing it would shift every existing step sequence, and it is still what protects `Particle.static_residuals`, whose frozen forward-only step schedule cannot be extended backwards.
- **A retarded time that still falls outside the integrated span now raises** rather than silently returning a clamped extrapolation of the first step. This replaces the `LTT/dt_step` heuristic warning on the dense paths, which fired on a quantity that turned out to be a poor proxy for the harm it was meant to flag (measured log-log correlation with the actual error: -0.29; a large ratio usually means a *distant* object, whose position errors subtend small angles). The new check reports the condition that actually matters after the fix -- whether the buffer covers the emission time -- and can only trigger when the object's topocentric distance more than doubles between the state epoch and an observation. The fully-jitted `System(observations=...)` callables cannot run a host-side check and rely on the backward padding alone; `warn_if_ltt_extrapolating` survives for `static_residuals`, which does still extrapolate near its epoch.
- Internal API: `make_ltt_propagator` now takes the whole dense-output buffers for both directional passes (as the new `DenseOutput` namedtuple) plus the epoch and the observation time, instead of a single pre-gathered step; `jorbit.integrators.stitched_dense_buffers` returns those buffers from the stitching loop; `dense_position` evaluates the trajectory at an arbitrary time within them. `stitched_per_query_gather` keeps its signature and return value.

**1.6.2 (09/2026)**

- **Added `System.model_radec_with_status`, which returns the per-observation "did the integration reach this time" mask that `model_radec` computes and discards.** jorbit's two IAS15 dense-output paths have different truncation semantics, and which one you get depends on whether you need a derivative: the `integrate`/`ephemeris` methods stitch as many dense-output chunks as the span requires and cannot truncate, while the `System(observations=...)` callables run inside one buffer per direction so that they can be traced and differentiated, and report an over-long arc by poisoning the unreached observations to `NaN`. A downstream user generating Fisher-information labels with `jax.jacfwd` through `model_radec` hit that `NaN` on a small fraction of long-arc rows and had no way to confirm the cause, since a `NaN` acceleration or a degenerate step produces the same symptom. The new callable returns `(ras, decs, reached)` — the same coordinates as `model_radec` plus the `(n_obs,)` boolean mask — so truncation (`reached` False) is positively identifiable rather than inferred. It is a separate jitted function, not a flag on `model_radec`, so callers that never ask for the status never compile for it; `model_radec` itself is untouched.
- **Added `System.probe_span`, a public wrapper around the existing `ias15_span_probe`.** The probe answers "would this span overflow the dense-output buffer at this `ias15_max_steps`?" with one cheap forward integration and no autodiff. It already backed the detect-and-raise guards in `Particle.ephemeris(uncertainty=True)` and `Particle.max_likelihood`, but reaching it for a `System` meant assembling five private attributes by hand. The `System` observation-scoring callables are deliberately still not guarded automatically: they are compiled once and scored on candidate states supplied as arguments, so a probe inside them would force a device sync and a full extra integration on every likelihood evaluation. Calling `probe_span` once, before committing to a fit or a Jacobian, is the intended pattern; note the answer describes the System's current state, so a sampler that wanders onto a more demanding orbit can still truncate. `ias15_span_probe`'s docstring, which claimed a likelihood-path guard that was never wired, has been corrected.
- No change to any step sequence, compiled program, or existing return value. Both additions are diagnostics; the truncation contract of the `loglike`/`chi2`/`residuals`/`model_radec` callables (`-inf`/`+inf`/`NaN`) is exactly as it was in 1.6.1. Note that if you are sizing `ias15_max_steps` by hand, the step count returned by `integrate`/`ephemeris` under `return_steps=True` is a conservative upper bound for the same arc: it sums accepted and rejected iterations across both directional passes, where `ias15_max_steps` counts accepted steps in one direction.

**1.6.1 (09/2026)**

- **Bug fix: the Yoshida leapfrog integrators (`"Y4"`, `"Y6"`, `"Y8"`) always stepped forward in time.** `leapfrog_evolve` took `jnp.abs(dt)`, so any integration to a time before the state's epoch marched the wrong way — and because the state then moved *away* from the requested times, the error compounded every step and grew as the step size shrank (up to ~1e+03 AU at `dt` = 0.1 d, and NaN at 0.01 d). The sign was the only thing wrong: the Yoshida C/D coefficient vectors are palindromic and the substep times are symmetric about the midpoint, so a negative step is the exact inverse of the positive one. Backward and epoch-straddling arcs now agree with IAS15 to ~1e-15 AU. **If you ran a leapfrog integration to any time before the epoch, those results were wrong.** IAS15 was never affected.
- Two smaller leapfrog bugs, both reported from downstream use. `System.ephemeris` raised `"scan got values with different leading axis sizes"` for any `max_step_size` below the observation spacing, because `system.ephem._ephem` scanned `on_sky` over the pre-expanded time array while the positions had already been gathered down to the requested times. And `create_leapfrog_times` appended index 0 for a repeated timestamp rather than the index it had just written, so two observations sharing an epoch silently both returned the state at the first expanded time. A `max_step_size` of zero or less now fails at construction instead of overflowing int32 inside `create_leapfrog_times`.
- **`System` now provides `loglike`/`residuals`/`chi2`/`model_radec` on the leapfrog paths**, via a `_model_leapfrog` sibling of the bounded-arc IAS15 model; the residual/chi-square/log-likelihood arithmetic stays on a single shared path. Relatedly, `Particle.loglike` now uses native reverse-mode AD for leapfrog rather than the `jacfwd`-backed custom VJP that the IAS15 `while_loop` forces (roughly 6x fewer passes per gradient), and `Particle` and `System` now agree that `return_steps` on a leapfrog path means the length of the expanded schedule rather than `None`.
- Documented three previously-silent leapfrog properties: `interpolate` is a no-op on those paths, the expanded step schedule is non-uniform so they are not symplectic in practice, and they support reverse-mode AD where IAS15 does not.

**1.6.0 (08/2026)**

- **Behavior change: the default IAS15 step scheduler is now "global" everywhere; "prs23" remains available as an option.** Prompted by a user report: the PRS23 controller can lose accuracy over many revolutions of a short-period orbit. Round-tripping a sub-AU orbit (a ~0.65 AU, period ~190 d) out and back over ~5-10 revolutions under "prs23" left position errors as large as ~1e-4 AU where "global" held ~1e-13 AU, and the "prs23" error is non-monotonic in the integration span — the signature of a step-schedule pathology at particular epochs rather than smooth error accumulation. At typical NEO distances the observed error reaches arcseconds on-sky against sub-arcsecond astrometric uncertainties, enough to corrupt likelihoods. Until the mechanism is understood, "global" (the controller from the original IAS15 paper) is the safer default: it degraded smoothly on every orbit tested. Concretely, `Particle.__init__` and the new `System.__init__` argument below now default to `"global"`, and the previously hardcoded `"prs23"` in the `System` observation-based forward model now follows the constructor. **Step sequences (and thus results, at the integration-error level) will differ from previous versions**; pass `step_scheduler="prs23"` to recover the old behavior.
- **`System.__init__` now accepts `step_scheduler`, threaded through to the observation-based forward model.** Previously the fast `loglike`/`residuals`/`chi2`/`model_radec` callables hardcoded "prs23" with no way to override, so those likelihoods could not be made consistent with astrometry generated under "global". The `step_scheduler` argument of the `System.integrate`/`System.ephemeris` methods is now an optional per-call override defaulting to None, meaning "use the scheduler the System was constructed with".
- Documented (in the `ias15_evolve` and `System.ephemeris` docstrings) that adaptive-IAS15 outputs are only piecewise-smooth in the initial state: an infinitesimal state change can change the realized step sequence, leaving discontinuities at roughly the integrator tolerance. Forward-mode AD differentiates the realized step sequence and is exact; finite differences of any scalar built from these outputs are silently unreliable in weakly-constrained directions (a user reported central differences of a single-tracklet loglike coming out ~50x off with the wrong sign). Behavior is unchanged — the hazard is now stated.

**1.5.2 (08/2026)**

- **Added an `ias15_max_steps` knob to `Particle` and `System` that sizes the IAS15 dense-output buffer to the arc.** The dense-output buffers were unconditionally allocated at `IAS15_MAX_DYNAMIC_STEPS` (15000) accepted steps, so a short arc that needs 1-3 steps still paid for zeroing multi-GB buffers on every forward-model call (and again for the tangents under autodiff) — an ~18x slowdown observed for a 50-minute arc at 512 particles. The buffer depth is now a static argument on `ias15_evolve`/`ias15_evolve_with_dense_output`, threaded through the stitched helpers, `_ephem_ias15_bounded`, and `create_system_forward_model`, and exposed as `ias15_max_steps` on the `Particle`/`System` constructors. The default (None -> 15000) leaves all existing callers bit-identical. The nominal `integrate`/`ephemeris` methods stitch extra chunks as needed, so a small buffer never truncates them; the `System(observations=...)` `loglike`/`chi2`/`residuals`/`model_radec` callables keep their loud truncation contract (`-inf`/`NaN` via `reached_mask`), so an undersized buffer can never return finite-but-wrong likelihoods. Note that the step schedule is shared across a batch, so one dynamically-pathological particle truncates the whole batch — group heterogeneous batches by dynamical timescale before shrinking the buffer.
- **Integrating past the loaded ephemeris window now fails loudly instead of returning garbage.** Out-of-window queries wrap/clamp the Chebyshev interval index to wrong-era coefficients, so the perturber positions stay finite and smooth: depending on the orbit this either stalled the integrator into the generic "IAS15 interpolation stitching made no forward progress ... (e.g. a NaN acceleration or a degenerate step)" error (sending users hunting for a dynamics bug), or — worse — marched straight through and silently returned wrong positions. Two fixes: (1) `Particle._times_to_offsets`/`System._times_to_offsets`, which every public method funnels its query times through (including the observation times behind the likelihood paths and the `System` forward model), now validate the requested times plus the reference epoch against the actually-loaded ephemeris span (recovered from the acceleration function's bound `EphemerisProcessor` data) and raise a `ValueError` naming the window and the `earliest_time`/`latest_time` constructor arguments that widen it; ephemeris-free (custom or Keplerian) gravity is unaffected. (2) The no-progress error path in the stitching loop performs the same bound check as a backstop and names the exceeded bound when the stall sits at the window edge.

- **Behavior change: `System` now actually honors `de_ephemeris_version` in its force model.** `System` accepted, documented, and stored the flag, and used it for observer positions in `System.ephemeris`, but `System._setup_acceleration_func` constructed all five built-in `Ephemeris` objects without passing it. Since `Ephemeris` defaults to `"440"`, every `System` integrated under DE440 regardless of what was requested — silently, and with no warning. The result was physically inconsistent: a `System` built with `de_ephemeris_version="430"` produced DE430 observer positions against DE440 dynamics, and because the discrepancy grows slowly from zero it was easy to mistake for ordinary integration error. `System` also now validates the value the way `Particle` always has, so an unsupported version raises instead of falling through to DE440. **If you have been passing `de_ephemeris_version="430"` to `System`, your results will change** — they were DE440 before and are DE430 now. `Particle` was never affected.
- **Behavior change: `jorbit.utils.mpc.unpack_epoch` now returns TT, not UTC.** MPCORB epochs are defined in TT — the MPC's *Export Format for Minor-Planet Orbits* specifies columns 21-25 as "Epoch (in packed form, .0 TT)" — but the decoded `Time` was tagged `scale="utc"`. Every epoch decoded from MPCORB was therefore mis-placed by TT-UTC (69.184 s as of 2026), a pure systematic worth roughly 1300 km along-track (~1.2 arcsec) for a main-belt object and 1960 km (~27 arcsec) for an NEO — far above jorbit's ~1 mas accuracy target. Times returned by this function now shift by 69.184 s relative to 1.5.0. Nothing inside jorbit called `unpack_epoch`, so no other behavior is affected; note that the observation dates parsed by `read_mpc_file` are correctly UTC, since the 80-column observation format differs from MPCORB in exactly this respect.
- `Particle.is_observable` built its Sun-position `Ephemeris` without `de_ephemeris_version`, so it mixed a DE430 observer with a DE440 Sun when the particle was set to DE430. Same class of bug as the `System` one above, much smaller amplitude (solar elongation tolerates a few km of Sun position easily), now consistent.
- Documented a known limitation that was previously silent: `Particle.static_residuals` always uses the DE440 "default solar system" dynamical model, regardless of the `gravity` and `de_ephemeris_version` passed to `Particle`. This is because `create_static_default_acceleration_func` is currently the only static acceleration function in `jorbit.accelerations`; there is no static counterpart to "newtonian planets", "gr planets", etc. Behavior is unchanged — the limitation is now stated in the `Particle` docstrings, in `precompute_likelihood_data`, and in the MCMC tutorial. Use `Particle.residuals` if you need the model you asked for.
- Fixed `jorbit.__version__`, which still read `"1.4.2"` when 1.5.0 shipped. The `__init__.py` and `pyproject.toml` version literals are maintained independently, so a test now asserts they agree.

**1.5.0 (07/2026)**

- **Major memory fix: JIT compilations no longer embed the JPL ephemeris (and other large arrays) as per-compilation constants.** The acceleration-function factories in `jorbit.accelerations`, the per-`Particle` `residuals`/`loglike` callables, the per-`System` forward-model callables, and the static-residuals pipeline all previously captured large arrays (most notably the ephemeris Chebyshev coefficients) in Python closures. JAX bakes any concrete array touched during tracing into the compiled executable as a constant, so every distinct compilation retained its own ~150 MB copy for the life of the process — enough to OOM CI runners (and any long-lived session creating many `Particle`/`System` objects). All such data now flows through `jax.tree_util.Partial`-bound arguments into shared, module-level jitted functions: buffers are shared process-wide and instances with matching shapes reuse compilations. Together with a new per-module JIT-cache-clearing test fixture, peak test-suite memory drops from ~19 GB to ~5.5 GB, and first-call (compile) times for the likelihood/gradient paths roughly halve; steady-state runtime of likelihoods and gradients is unchanged (verified with back-to-back benchmarks of `loglike`, `residuals`, `static_residuals`, their gradients, and the `System` forward model). Note one small behavioral difference: `Particle.residuals`/`Particle.loglike` and the `System` forward-model callables are no longer pre-wrapped in an extra `jax.jit` (their internals are already jitted); wrapping them in your own `jax.jit` still works, but re-introduces the constant-embedding for that one compilation.
- Fixed `EphemerisPostProcessor.tree_unflatten` running `jnp.concatenate` on its children during unflattening, which crashed when JAX rebuilds the pytree with placeholder leaves (e.g. under `jax.vmap` with `in_axes=None`). `log_gms` is now stored as a pytree child and unflattening is purely structural.
- Added protections for integrations/ephemerides generated via the front end `Particle` and `System` classes no longer silently truncate when an integration requires more steps than allocated in 1) the cap of 10k steps between time steps and 2) the cap of 15k total accepted steps when using "interpolation". The actual caps remain in the back end implementations.
- Fixed a bug in the `Particle.integrate_or_interpolate` method that would produce garbage results on very long backwards integrations.

**1.4.0 (05/2026)**

- Added `uncertainty=True` as an option to `Particle.ephemeris` that returns the propagated on-sky covariance in addition to the propagated state. This is implemented by computing the Jacobian of the dynamics using forward autodiff, then linear error propagation using the initial covariance on the `CartesianState` or `KeplerianState`.
- Several misc bug fixes found by Claude's recent code audit, including some precision loss issues when combining `Observation` objects and array shape mismatches.

**1.3.0 (05/2026)**

- Instead of taking an IAS15 step to the exact observation times, the `static_step` now takes natural IAS15 adaptive steps and evaluates the relevant polynomials based on the b coefficients to compute positions/velocities at arbitrary times within a step. This cuts down the number of IAS15 steps substatially when observations are spaced within a typical maximum-allowable IAS15 step, or ~30 days. This involves lots of changes to the internal `ias_15_evolve` function and the creation of some new internal helpers like `ias15_evolve_with_dense_output`, `ias15_evolve_forced_landing` and `interpolate_from_dense_output`.
- Added option for Keplerian-only motion to `Particle` and `System`. This is significantly faster than the full N-body simulations and is useful for both short-term motion and outer solar system applications where the perturbations are small.
- Add the `.is_observable` method to `Particle` objects which checks whether the particle is at least a certain angular distance from the Sun at given times from given observatories.
- Modified `on_sky` to take optional `ltt_position_fn` instead of always defaulting to the Taylor expansion. Can be used to "interpolate" using the above-mentioned b coefficients.
- Changed the internal representations being absolute and relative time. No external API changes, but now `Particle` and `System` objects work in relative times by default, only converting to absolute times when necessary for ephemeris queries. This preserves some precision by not storing all the extra digits in mjd/jd.
- Add the "global" IAS15 step size controller in addition to the default "PRS23" controller.
- Misc bug fixes and code cleanups.

**1.2.0 (02/2026)**

- Major refactor of ias15.py, no longer resembles the original REBOUND implementation. Removed IAS15Helper, but otherwise no API changes.
- Major refactor of ppn_gravity, the outputs are unchanged but now unnecessary perturber-perturber interactions are excluded.
- Added a "static" version of IAS15 that uses fixed step sizes and a fixed number of predictor-corrector iteratins. Also added the ability to pre-compute perturber positions/velocities/ppn-specific acceleration terms at every (sub)time step prior to integrating. These features are intended to speed up likelihood evaluations in orbit fitting applications where we expect only small changes to the initial conditions of a test particle. This dramatically accelerates both likelihood and gradient evaluations. The "integrate", "loglike", and "ephemeris" attributes of Particle remain unchanged for now, but a new method called "static_residuals" has been added that uses these new tools.
- Addition of `fixed_perturber_positions`, `fixed_perturber_velocities`, and `fixed_perturber_log_gms` to `SystemState`. These quantities can be used in different acceleration functions to indicate that perturber-perturber interactions should be ignored and that gradients with respect to these quantities don't need to be tracked.
- Added option to select DE ephemeris version (DE430 or DE440) when creating `Ephemeris` and `Particle` objects. Updated relevant tutorials/tests.
- Dropped support for Python 3.9.
